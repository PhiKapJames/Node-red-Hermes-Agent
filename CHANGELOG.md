# Changelog

## Unreleased

Nothing in this section is released: no version was bumped or tagged, and nothing here has been exercised against a live Hermes Agent server.

**Async admission backoff.** The Queue `retryDelay` setting is now the *base* wait: retries after an HTTP 429 admission response grow exponentially from it (2 s, 4 s, 8 s, ...), growth is capped at 60 s, and every wait is clamped to the run deadline remaining. Other retryable admission failures keep repeating the base delay. The `retrying` lifecycle event gained an additive `delayMs` field. Cancellation during a retry wait and the cancellation barrier are unchanged.

**Server diagnostics.** A Control node can be set to **Probe** capabilities (`GET /v1/capabilities`) or readiness (`GET /health/detailed`) through its own Connection. The summary is a closed projection of booleans, clamped counts and short single-line strings with the Connection key treated as a secret; nested upstream maps are never copied. A probe never touches queue state, a failed probe never pauses the queue (it reports `hermes.probe.stale: true` and `approvalSupported: false`), and an unreported feature flag is reported as unsupported, never as support. Probes are fixed-only: `msg.hermesControl.action: "probe"` is rejected.

**Approval observability.** Async runs that stop for permission now report `waiting_for_approval` on lifecycle output 2 with `approvalRequestId` and the server-advertised `approvalChoices`. A new Queue setting `includeApprovalPreview` (default **false**, never message-settable) additionally puts bounded, credential-redacted `approvalCommand`/`approvalDescription` text on that event. At most one approval decision is pending per run at a time (server contract); the projection never fabricates an unusable decision id.

**Approval relay (opt-in, fail-closed).** A Control node can be set to **Answer approval**: it requires `allowApprove: true` **and** a non-empty `approvalChoices` list (both default to no, so upgrades, imports and legacy flows enable nothing), and a message must name both `msg.hermesControl.requestId` and `msg.hermesControl.approvalRequestId` plus a `choice` that is permitted by the node **and** advertised by the server for that decision. Refusals are local with zero HTTP requests; the POST goes to the Connection admitted for that job, is never replayed, and never frees the queue slot early. A decision answered elsewhere surfaces the server's 409 (`approval_not_pending`/`approval_not_active`) on the error output as the correct outcome; it is never retried. `session`/`always` grants persist server-side and are not revocable from Node-RED. Approvals are fixed-only: `msg.hermesControl.action: "approve"` is rejected.

**Semantics settled.** `msg.hermesControl.force` is the `reset` action's override and is read for that action alone; every other action ignores it. Documentation (README, runbook, adapter contract, AGENTS.md) now matches, and a new docs test asserts the documented action list against `CONTROL_ACTIONS` exported by `lib/queue.js`, so the lists cannot silently drift again. The earlier claim that interactive approval submission is not implemented is retracted: relaying an explicit human decision is implemented, while choosing a decision automatically remains unimplemented and contrary to this package's design.
**Connect-phase transport failures are provably not dispatched (fixes #12).** A Hermes restart, a stopped service or a dropped VPN link previously paused the shared queue and forced every later message to fail `QUEUE_UNCERTAIN` until an operator opened the editor for a force reset. A transport failure whose error carries a connect-phase signature — `syscall` `connect` or `getaddrinfo`, or `ERR_DNS_MOVE_LIST_NOTFOUND`, covering `ECONNREFUSED`, `ETIMEDOUT` while connecting and an unresolved host — is now classified as **provably not dispatched**: the job fails with `retryable: true` and `remoteUnknown: false`, the queue stays running and admits the next request after its cooldown, and no `recover` or force reset is required. Classification reads the thrown error rather than the optimistic dispatched flag, so it cannot widen uncertainty; everything that can still mean remote execution is unchanged — post-dispatch drops (`ECONNRESET`, `ECONNABORTED`, `ERR_STREAM_WRITE_AFTER_END`, `EPIPE`, socket hang up), `HTTP_TIMEOUT`, post-dispatch `408`/5xx, `INVALID_RESPONSE` without a `run_id` and `QUEUE_CLOSED` during admission all remain uncertain, and the non-force reset barrier is untouched. The rule keys on libuv `syscall` values observed on Linux and is pinned by platform-independent unit tests, alongside real-socket tests proving the queue stays usable after a refused connect. Bearer redaction, no-redirect behaviour, the request/response size limits and stable `Idempotency-Key` reuse across admission retries are unchanged; no queue settings and no flow-JSON changes are introduced.

## 0.4.0-beta.1 — Prerelease: queue status bounds and log-safe error messages

First public prerelease; no earlier version was tagged or published. Since 0.3.0: the Queue `status` snapshot now keeps `pending` as the exact waiting count while `queued` is a bounded FIFO prefix of at most 50 summaries, with a new always-present `queuedTruncated` boolean; integrators must use `pending`, never `queued.length`, for backlog decisions. A retained uncertain job is reported as `uncertain.status: "uncertain"` for as long as the queue holds it. Redacted error messages now have every CR/LF run collapsed to one space, so an upstream error body cannot forge additional CR/LF-delimited Node-RED log entries and `msg.hermes.error.message` contains no CR or LF; tabs and Unicode separators are intentionally preserved. Adds the agent integration runbook (docs/agent-integration.md) and AGENTS.md. Node.js 24.0.0+ and Node-RED 5.0.0+ are required. Validation to date covers lint, unit tests, localhost HTTP fixtures, real isolated Node-RED 5 process tests and CI on Node 24.0.0/24/26; this prerelease has **not** been installed in a live Home Assistant/Node-RED deployment or exercised against a live Hermes Agent server, and must not be treated as production-ready.

## 0.3.0 — Node.js 24+ modernization

Breaking: Node.js 24.0.0+ is now required alongside Node-RED 5+. Refactor native HTTP around async response streams and composed abort/deadline signals while retaining TLS and size limits. Use abortable promise timers for queue polling, cooldown and retry waits, simplify input/shutdown handlers with async/await, and cancel late known admissions on shutdown. Replace the deprecated Node-RED test helper with isolated embedded Node-RED process fixtures using node:test. CI covers the exact Node 24 floor, current 24.x and Node 26 forward compatibility. No runtime dependencies, credential changes, server-profile changes or radio-specific policy are added.

## 0.2.0 — Node-RED 5 and later only

Breaking release: require Node-RED 5.0.0+ and Node.js 22.9.0+. Remove Node-RED 4 support, runtime callback shims, and the previous Queue `requestTimeout` compatibility path; `asyncRequestTimeout` is the only Queue HTTP-wait setting (default 30 seconds), while the Connection `requestTimeout` remains unchanged. Simplify asynchronous queue promises using native `Promise.withResolvers()`, update the example Inject nodes to include fully typed `props[]`, and run the CI matrix exclusively on Node-RED 5 with Node.js 22/24. Existing transport-independent request contracts, credentials, session isolation, and reset/cancellation safeguards are retained. See the README for migration instructions; no Hermes server or radio-specific configuration changes are required.

## 0.1.0 review corrections

Correct canonical repository links and model-override/memory-scope documentation. Preserve and optionally map author bot flags, migrate the Queue async-request timeout setting compatibly, support more than ten shared Agent listeners, and use traced Node-RED done(error) handling without duplicate Catch notifications. Add standard node help sections, development-only ESLint, review regressions, and CI concurrency with one package artifact. Non-force reset retains its cancellation barrier; new tests protect it. No application-specific policies or memory configuration changes are introduced.

## 0.1.0

Initial transport-independent implementation. Adds shared profile credentials and TLS, a generic request mapper, sync chat and async Runs, a bounded shared FIFO, per-client sessions, queue controls, idempotent async admission retries, explicit uncertainty handling, and three separate Agent outputs. Model defaults are left to Hermes. Replies are not truncated or split. Includes examples, unit/mock-server tests, and CI runtime integration tests for Node-RED 4 and 5.
